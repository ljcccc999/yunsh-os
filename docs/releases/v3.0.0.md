# YUNSH OS v3.0.0

YUNSH OS v3.0.0 packages the liquid-glass spatial desktop, Orbit system agent,
Android desktop integration, and the first-install path into a refreshed
Raspberry Pi image.

## Highlights

- Circular white liquid-glass application surfaces with optical-display-safe
  contrast and rounded system panels.
- Interruptible task-switcher and window transitions that preserve the current
  presentation state when switching or reopening apps.
- Orbit remains a circular O at rest. During system-tool work it expands into a
  top-right activity island; voice chat grows a speaking waveform from the O
  opening. Tool approvals are available directly inside the island, including
  one-time and always-allow choices where safe.
- Orbit settings provide explicit all-permission and all-disable controls;
  destructive operations still require fresh local confirmation.
- Android applications discovered by the runtime appear as individual desktop
  entries, while Android preparation remains independent of desktop startup.
- Factory reset verifies the current local password and resets it only after
  the final confirmation.
- The macOS flasher defaults to the v3.0.0 image, validates SHA-256 and XZ
  integrity, and performs a non-writing `--check` mode.

## Validation

The rebuilt image passed static QML, Python, and shell checks; ext4 and
boot-partition injection checks; required-file and systemd-link checks;
XZ/SHA-256 integrity; and the desktop flasher's non-writing verification mode.
Its boot partition includes a read-only confirmed Raspberry Pi 5 firmware,
kernel, initramfs, DTB, and overlay payload; activation markers and runtime
user state were not copied. The rebuilt archive itself was not reflashed onto
hardware in this rebuild, so the hardware notes below refer to the earlier
v3.0.0 regression evidence rather than a fresh test of this exact hash.

Image SHA-256: `cffc5c4b1f1b106f2424dad25badc98c4f613ac912f677f04c8b17943602d3fc`

OTA SHA-256: `d2360bd964028c0737ff5be02ec4410ecc582f7476445c0f3fbb67ffda702405`

A previous v3.0.0 build reached the multilingual activation surface over SSH
regression, and a capture from its `/dev/fb0` contained the YUNSH OS v3.0.0
activation page and Continue button. On this device the VC4 DRM clock provider
does not initialize, so the verified display path is Qt software `linuxfb`
over the firmware framebuffer. The same real-device regression also confirmed
the YUNSH Link BLE GATT service is advertising and the controller is pairable.
The activation flow now separates transient connection from persistent phone
authentication: after the iPhone verifies the one-time key in YUNSH Link, the
Pi enables its normal “Continue” action; a trusted iPhone may reconnect without
entering the key again.
Bluetooth settings also exposes the current unexpired one-time key and can
generate a new key for pairing the same iPhone with another Pi. Generating a
new key does not remove an existing trusted device.
YUNSH Link keeps Pi entries keyed by their BLE device identity rather than by
the temporary key, so a changed key does not duplicate one Pi and two Pis are
still shown separately even if their keys happen to match. Switching back to a
Pi that already trusts the iPhone does not require another key entry.
The iPhone can revoke the active Pi binding through two explicit confirmations;
the Pi then removes that phone's trust and invalidates the old key.
This validates visible UI, service startup, and the Pi-side BLE advertisement,
not accelerated DRM/GPU/Wayland output or a complete iPhone pairing session.
Bluetooth motion hardware, microphone, Android binder/GPU behavior, and
optical-display-specific behavior still require their corresponding hardware
validation.
